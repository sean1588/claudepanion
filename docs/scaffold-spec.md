# Companion Scaffold Specification

> Reference doc. Describes the current scaffold contract (v2, `contractVersion: "2"`). The design that produced this contract is captured in [`docs/superpowers/specs/2026-05-09-scaffold-consistency-design.md`](superpowers/specs/2026-05-09-scaffold-consistency-design.md). When the two disagree, this doc is canonical for what's *shipped*; the design doc is canonical for *why*.

---

## 1. Overview

A **companion** is a small app that lives inside the claudepanion host. There are two kinds.

| Kind | Lifecycle | Form | Artifact | Pages |
|---|---|---|---|---|
| `ui` | yes (`pending → running → completed/error`) | yes | yes (markdown) | Form, List, Detail |
| `tool` | none | none | none | About (auto) |

### File shape — `kind: "ui"`

```
companions/<slug>/
├── manifest.ts          ← authored
├── types.ts             ← authored (InputSchema + optional ArtifactExtras)
├── index.ts             ← AUTO-GENERATED by scaffold CLI
└── server/
    └── tools.ts         ← authored (defineTool entries)

skills/<slug>-companion/
└── SKILL.md             ← authored (the playbook)
```

Five files; three with creative content. No `form.tsx`, `pages/Detail.tsx`, or `pages/List.tsx` in the common case — those are rendered by host primitives. Override files exist; see §8.

### File shape — `kind: "tool"`

```
companions/<slug>/
├── manifest.ts          ← authored
├── index.ts             ← AUTO-GENERATED
└── server/
    └── tools.ts         ← authored

skills/<slug>-companion/
└── SKILL.md             ← authored (typically a brief "use these tools when X" guide)
```

No `types.ts`; no input/artifact lifecycle.

### Where state lives

User state is stored under `~/.claudepanion/`:

| Path | Purpose |
|---|---|
| `~/.claudepanion/data/<slug>/<id>.json` | Per-entity lifecycle JSON (one file per run, atomic writes) |
| `~/.claudepanion/cache/` | Reserved for future use |

Decoupling state from cwd means multiple checkouts of the host share a single user-local data store.

### Host primitives the companion plugs into

- `<CompanionForm>` — schema-driven form (§9)
- `<MarkdownArtifactPanel>` — Detail page renderer (§9)
- `<DefaultListRow>` — List page row renderer (§9)
- `defineTool()` — typed proxy-tool declaration (§9)

## 2. Companion lifecycle (`kind: "ui"`)

```
pending  ──►  running  ──►  completed
              │
              └──────►  error
```

| State | Meaning | UI surface |
|---|---|---|
| `pending` | Form submitted; entity created; awaiting Claude Code handoff | Slash-command invitation |
| `running` | Skill is executing | Live log tail, status pill, statusMessage |
| `completed` | Artifact saved | Detail page renders the markdown |
| `error` | Unrecoverable failure | `errorMessage` + `errorStack` shown |

State transitions go through the companion's `mcp__claudepanion__<slug>_*` tools (`_update_status`, `_append_log`, `_save_artifact`, `_fail`). The REST API is read-only for entity state.

### Re-engagement

A completed entity can be continued by hitting `POST /api/entities/:id/continue` (the host UI's "Continue" button). The companion's skill detects continuation when `entity.artifact !== null` at load time and `entity.input.description` carries the redirection.

State for a slug lives at `~/.claudepanion/data/<slug>/<id>.json` and is owned exclusively by the companion's MCP tools.

## 3. The Manifest

`companions/<slug>/manifest.ts` exports `manifest: Manifest`.

### Required fields

| Field | Type | Notes |
|---|---|---|
| `name` | `string` | Slug matching `^[a-z][a-z0-9-]*$`. Must equal directory name. |
| `kind` | `"ui" \| "tool"` | (`"entity"` is removed in v2.) |
| `displayName` | `string` | Title-cased, used in nav + page headers. |
| `icon` | `string` | One emoji. Shown in sidebar + headers. |
| `description` | `string` | One sentence describing what the companion does. Specific, not generic. |
| `contractVersion` | `"2"` | Pinned. Validator rejects other values. |
| `version` | `string` | SemVer. Bumped on iterate runs. |

### Optional fields

| Field | Type | Notes |
|---|---|---|
| `requiredEnv` | `string[]` | Env vars the companion's tools require. Validator warns if a tool reads `process.env.X` not in this list (or vice versa). |
| `optionalEnv` | `string[]` | Env vars the companion uses if present but doesn't require. |
| `actionLabels` | `{ runCta?: string; ... }` | UI overrides for default button copy. |

### Validator rules (selected)

- `manifest.name` must equal the directory slug.
- `kind` must be `"ui"` or `"tool"`.
- `contractVersion` must equal `"2"` (the host's `SUPPORTED_CONTRACT_VERSION`).
- For `kind: "ui"`: `types.ts` exporting `InputSchema` is required.
- Tool names in `server/tools.ts` must be prefixed with the slug, hyphens converted to underscores.

```ts
import type { Manifest } from "../../src/shared/types.js";

export const manifest: Manifest = {
  name: "pr-reviewer",
  kind: "ui",
  displayName: "PR Reviewer",
  icon: "👀",
  description: "Review a GitHub PR — fetch the diff, flag risky changes, optionally post a structured review back.",
  contractVersion: "2",
  version: "0.1.0",
  requiredEnv: ["GITHUB_TOKEN"],
};
```

## 4. The Input Schema (`kind: "ui"`)

`companions/<slug>/types.ts` exports `InputSchema`.

### Constraints

- Must be a `z.ZodObject` or `z.ZodDiscriminatedUnion`. The validator enforces this.
- `.describe()` provides the field label (the form uses it).
- `.meta({ ui: { ... } })` provides rendering hints.

### Field types and default rendering

| Schema | Default UI | `meta({ ui })` overrides |
|---|---|---|
| `z.string()` | `<input type="text">` | `kind: "select"` (with `options: [...]` or `optionsFrom: "tool_name"`); `kind: "searchableSelect"`; `kind: "textarea"`; `kind: "password"` |
| `z.string().datetime()` | `<input type="datetime-local">` | — |
| `z.number()` | `<input type="number">` | `kind: "slider"` with `min`/`max`/`step` |
| `z.boolean()` | `<input type="checkbox">` | — |
| `z.enum([...])` | `<select>` of enum values | — |

### `optionsFrom` semantics

A field with `meta({ ui: { kind: "select", optionsFrom: "tool_name", argsFrom: ["region"] } })` populates by POSTing to `/api/tools/<slug>/<tool_name>` with the named upstream fields as args. When an `argsFrom` field changes, the dropdown refetches. Dependency cycles are rejected at load time.

The tool referenced by `optionsFrom` must have `sideEffect: "read"` (or unset). Write tools cannot drive form options — see §15.

### `group` semantics

Fields sharing a `group` value render side-by-side in a labeled row. Use for things like start/end datetime ranges.

```ts
import { z } from "zod";
import type { BaseArtifact } from "../../src/shared/types.js";

export const InputSchema = z.object({
  region: z.string().min(1).describe("AWS region"),
  alarmName: z.string().min(1).describe("Alarm")
    .meta({ ui: { kind: "select", optionsFrom: "list_alarms_in_alarm", argsFrom: ["region"] } }),
  startTime: z.string().datetime().meta({ ui: { kind: "datetime", group: "window" } }),
  endTime:   z.string().datetime().meta({ ui: { kind: "datetime", group: "window" } }),
});

export type Input = z.infer<typeof InputSchema>;
```

## 5. The Artifact (`kind: "ui"`)

Every run produces one artifact saved by `mcp__claudepanion__<slug>_save_artifact`.

### `BaseArtifact` contract

```ts
interface BaseArtifact {
  summary: string;        // required — list-row + Detail page header
  markdown: string;       // required — the canonical user-facing report
  errors?: string[];      // optional — non-fatal issues
}
```

Both `summary` and `markdown` are required. The validator rejects companions whose `_save_artifact` schema doesn't enforce them.

### Optional `ArtifactExtras`

Typed fields beyond `BaseArtifact`, for list-row badges or future programmatic use. Rendering is **always** `markdown` — extras are not for displaying.

```ts
export interface ArtifactExtras {
  prNumber: number;
  recommendation: "approve" | "request_changes" | "comment";
}

export type Artifact = BaseArtifact & ArtifactExtras;
```

If a companion has no list-row override and no programmatic consumers of typed fields, default to:

```ts
export type Artifact = BaseArtifact;
```

### Rendering

The host renders the artifact via `<MarkdownArtifactPanel>` (§9). The companion never writes JSX for the Detail page in the default case.

## 6. Proxy tools (`server/tools.ts`)

`companions/<slug>/server/tools.ts` exports `tools: CompanionToolDefinition[]`. Use `defineTool({...})` for each entry.

### `defineTool` shape

```ts
import { z } from "zod";
import { defineTool } from "../../../src/shared/define-tool.js";

export const tools = [
  defineTool({
    name: "pr_reviewer_get_pr",
    description: "Fetch PR metadata. Read-only.",
    sideEffect: "read",                   // "read" | "write"; defaults to "read"
    schema: { repo: z.string(), prNumber: z.number().int().positive() },
    async handler({ repo, prNumber }) {   // params type inferred from schema
      // ...
    },
  }),
];
```

The generic flows from `schema` to `handler.params` automatically — no manual type parameters, no `as unknown as` casts.

### Naming

- Tool name must start with `<slug-with-underscores>_`. The validator rejects others.
- Examples: slug `pr-reviewer` → `pr_reviewer_get_pr`; slug `cloudwatch-investigator` → `cloudwatch_investigator_query_logs`.

### Side-effect classification

- `sideEffect: "read"` — safe to call from the browser via `<CompanionForm>` `optionsFrom`. Default.
- `sideEffect: "write"` — host rejects browser calls. Must be invoked through the companion's skill, where the user is prompted to confirm.

Write tools must declare consequences explicitly in `description`. Bad: `"Post a comment to GitHub."` Good: `"Post a structured review to the PR. Visible to all collaborators on the repo and cannot be unsent. Requires GITHUB_TOKEN with 'repo' scope."`

### Error classification taxonomy

Tool handlers classify errors by mapping the SDK's error onto one of these prefixes:

| Prefix | Meaning | Skill action |
|---|---|---|
| `[config]` | Missing/expired credentials, missing IAM permission, missing env var | `_fail`; stop. User fixes env. |
| `[input]` | Bad ID, bad timestamp, malformed user input | `_fail`; stop. User fixes the form. |
| `[transient]` | Rate limit, network blip, 5xx upstream | Retry once; fail if still failing. |
| `[recoverable]` | Partial success | Log warn; append to `artifact.errors[]`; continue. |

Helpers in `src/shared/types.ts`: `configErrorResult(envName, fix)`, `inputErrorResult(msg)`, `transientErrorResult(msg)`, `errorResult(msg)`, `successResult(data)`.

### Error classifier pattern

The classifier is per-companion (copy-paste, not host-shipped). Pattern for a GitHub-backed tool:

```ts
function classifyGithubError(err: unknown) {
  const e = err as { status?: number; message?: string };
  const msg = e?.message ?? String(err);
  if (e?.status === 401 || e?.status === 403) return configErrorResult("GITHUB_TOKEN", `auth failed: ${msg}`);
  if (e?.status === 404 || e?.status === 422) return inputErrorResult(`not found / unprocessable: ${msg}`);
  if (e?.status === 429 || (e?.status ?? 0) >= 500) return transientErrorResult(`upstream: ${msg}`);
  return errorResult(msg);
}
```

For other services: auth/permission errors → `[config]`; bad-input/not-found errors → `[input]`; rate-limit/5xx errors → `[transient]`; partial-success errors → `[recoverable]`. The taxonomy is the contract; the per-service mapping is a copy-paste pattern.

## 7. The Skill body

`skills/<slug>-companion/SKILL.md` — the playbook Claude follows when the slash command fires.

### Frontmatter

```yaml
---
name: <slug>-companion
description: Use when the user pastes "/<slug>-companion <entity-id>" — <one specific sentence>.
---
```

`description` should be specific (what data, what action, what credentials), not generic ("Helps with X").

### Body structure

Most of the file is a host-canonical template. Only these parts are freeform per companion:

- The frontmatter `description`.
- The Step 4 ("Do the work") sequence — one sub-step per proxy-tool call, each followed by an `_append_log` line.
- Any write-tool permission stanzas embedded in Step 4.

### Write-tool permission stanza shape

For any `sideEffect: "write"` tool the skill calls:

> **Show the user the proposed write content in chat.** Ask: "Should I post/send/update this?" Wait for confirmation.
>
> If confirmed: call the write tool.
>
> If declined: skip the call; append `"user declined <action>"` to `artifact.errors[]` and continue.

This stanza appears as a sub-step *before* the write call in Step 4.

## 8. Override slots (escape hatch)

When a host primitive isn't enough, drop in a per-companion JSX file:

| Override file | Replaces |
|---|---|
| `companions/<slug>/form.tsx` | `<CompanionForm>` |
| `companions/<slug>/pages/Detail.tsx` | `<MarkdownArtifactPanel>` |
| `companions/<slug>/pages/List.tsx` | `<DefaultListRow>` |

**Filesystem-presence is the contract.** No flag in the manifest. The scaffold CLI's codegen for `companions/client.ts` checks for the file's existence; present → register the override; absent → register the default primitive.

Use overrides sparingly. Build's two-tab new/iterate form is the canonical example of an override worth keeping; most companions don't need any.

## 9. Host primitives

### `<CompanionForm>`

Lives at `src/client/primitives/CompanionForm.tsx`. Renders any `InputSchema` as a form.

```ts
function CompanionForm<T extends z.ZodTypeAny>(props: {
  schema: T;
  onSubmit: (input: z.infer<T>) => void | Promise<void>;
  companionSlug?: string;          // required if any field uses optionsFrom
}): JSX.Element
```

Field rendering follows the table in §4. Validation runs per-field on blur (single-field Zod parse) and full-schema on submit (`safeParse`). Submit button disabled while required fields are invalid. `optionsFrom` dropdowns handle their own loading/retry/error states.

### `<MarkdownArtifactPanel>`

Lives at `src/client/primitives/MarkdownArtifactPanel.tsx`. Renders any `BaseArtifact`.

```ts
function MarkdownArtifactPanel(props: { artifact: BaseArtifact }): JSX.Element
```

Layout: `summary` as the page H1 → optional "Notes during this run" callout listing `errors[]` → `<react-markdown>{artifact.markdown}</react-markdown>` (GFM enabled, raw HTML sanitized). Empty markdown → placeholder ("No markdown report generated").

### `<DefaultListRow>`

Lives at `src/client/primitives/DefaultListRow.tsx`. Renders one row of the List page.

```ts
function DefaultListRow(props: { entity: Entity<unknown, BaseArtifact> }): JSX.Element
```

Row content: `[status pill] {entity.id}  {artifact.summary ?? "<pending>"}  {relativeTime(entity.updatedAt)}`.

### `defineTool()`

Lives at `src/shared/define-tool.ts`. Type signature:

```ts
export function defineTool<S extends z.ZodRawShape>(def: {
  name: string;
  description: string;
  schema: S;
  sideEffect?: "read" | "write";
  handler: (params: z.infer<z.ZodObject<S>>) => Promise<McpToolResult>;
}): CompanionToolDefinition;
```

Types flow from `schema` to `handler` automatically.

## 10. Scaffold CLI

Entry: `bin/cli.js`. Implementation: `src/cli/`.

### Subcommands

| Command | Purpose |
|---|---|
| `claudepanion scaffold <slug>` | Bring `<slug>`'s files into a coherent registered state — full validate/deps/codegen/build/remount/self-check flow. |
| `claudepanion regenerate` | Re-derive registry files from disk (no build, no install). |
| `claudepanion remount <slug>` | Manual remount — POST `/api/internal/remount` for a running server. |

### `scaffold` stages

1. **`validate`** — slug regex; manifest type/version/kind; tools.ts tool-name prefix; required files present.
2. **`deps`** — walk tools.ts AST imports; `npm install` missing non-relative imports.
3. **`codegen`** — emit `companions/<slug>/index.ts`, regenerate `companions/index.ts` and `companions/client.ts`.
4. **`build`** — `npm run build` (`tsc` + `vite build`).
5. **`remount`** — POST `/api/internal/remount?slug=<slug>` to localhost:3001. Server-down is a non-fatal warning.
6. **`self-check`** — run validator + smoke runner in-process (bypassing MCP).

### Output (success)

```json
{
  "ok": true,
  "slug": "pr-reviewer",
  "kind": "ui",
  "stagesRun": ["validate","deps","codegen","build","remount","self-check"],
  "filesGenerated": ["companions/pr-reviewer/index.ts","companions/index.ts","companions/client.ts"],
  "dependenciesAdded": ["@octokit/rest@^21.0.0"],
  "selfCheck": { "validator": { "ok": true }, "smoke": { "ok": true } }
}
```

### Output (failure — Claude branches on `stage`)

```json
{
  "ok": false,
  "stage": "build",
  "error": "tsc failed: companions/pr-reviewer/server/tools.ts(42,7): error TS2322: ...",
  "remediation": "fix the type error in server/tools.ts and re-run scaffold"
}
```

| Stage | Cause | Remediation |
|---|---|---|
| `validate` | bad slug, manifest mismatch, missing required file | fix the named file; re-run |
| `deps` | npm install failed | check package name / network; re-run |
| `codegen` | filesystem error writing registry files | check permissions; re-run |
| `build` | tsc/vite failed | fix the named file; re-run |
| `remount` | server unreachable | start `claudepanion serve`; re-run |
| `self-check` | validator fatal or smoke shape error | read issues; fix; re-run |

## 11. Auto-generated files

Three files under `companions/` are emitted by the scaffold CLI:

| File | Contents |
|---|---|
| `companions/<slug>/index.ts` | Per-companion exports binding manifest + tools (3 lines, deterministic). |
| `companions/index.ts` | Host registry array, alphabetical-by-slug. |
| `companions/client.ts` | Browser dispatch table — registers form/detail/list overrides per slug; defaults otherwise. |

Each carries a banner:

```ts
// AUTO-GENERATED — do not edit; run `claudepanion scaffold <slug>` or `claudepanion regenerate`.
```

These files **stay tracked in git** so a fresh `git clone && npm install && npm run build` works without first running the CLI. Manual edits are flagged in PR review by the banner.

## 12. Data persistence

State lives in user home, not cwd:

| Path | Purpose |
|---|---|
| `~/.claudepanion/data/<slug>/<id>.json` | One file per entity. Atomic writes (write-temp + rename). |
| `~/.claudepanion/cache/` | Reserved for future use. |

Resolved via `path.join(os.homedir(), ".claudepanion", "data")` at server startup; created on first run if absent. The host owns these paths; companions don't read or write them directly — all access is through `mcp__claudepanion__<slug>_*` tools.

## 13. Watcher behavior (dev mode)

`src/server/reliability/watcher.ts` watches `companions/<slug>/manifest.ts` and `companions/<slug>/index.ts`. On change, it re-imports `dist/companions/<slug>/index.js` with cache busting and calls `registry.remount(fresh)`.

### Dist-mtime gate

Before `import()`, the watcher stats both source and `dist/` paths. If `dist.mtime < source.mtime`, it throws `DistStaleError`. The retry policy: debounced retries at 1s / 2s / 4s before giving up.

### `dev:tsc` health probe

On server start, the watcher checks `dist/.tsbuildinfo` recency. If stale, it logs:

```
[watcher] tsc --watch isn't running; companion changes won't be picked up. Run npm run dev:tsc.
```

### Structured failure logs

Every remount failure logs with stage tags. Stages: `dist-stale`, `import-threw`, `validation-failed`, `not-a-companion-module`. Format:

```
[watcher] <slug> remount failed at <stage>: <reason> (will retry: yes/no)
```

The watcher never silently keeps the old version. Every failure path logs why.

## 14. The `/api/internal/remount` endpoint

```
POST /api/internal/remount?slug=<slug>
```

- Validates slug regex.
- Calls the watcher's `triggerRemount(slug)`.
- Returns `{ ok: true, version }` on success or `{ ok: false, error }` on failure.

Localhost-only (rejects non-loopback origins). Used by the scaffold CLI's `remount` stage and by the `claudepanion remount` subcommand.

## 15. The `/api/tools/:companion/:tool` endpoint

```
POST /api/tools/<slug>/<tool_name>
Content-Type: application/json
{ "args": { ... } }
```

Behavior depends on companion kind and tool's `sideEffect`:

| Kind | `sideEffect` | Browser callable? | Use case |
|---|---|---|---|
| `ui` | `"read"` (or unset) | yes | `<CompanionForm>` `optionsFrom` dropdowns |
| `ui` | `"write"` | **no** — host returns 403 | Must go through skill where user confirms |
| `tool` | any | yes | Try-it panel on About page |

The browser-callable subset is what makes schema-driven forms work — a dropdown that needs live data fetches it via this endpoint, parameterized by other form fields per `argsFrom`.

## 16. Tool-kind companions

Three authored files; no input/artifact lifecycle.

```
companions/<slug>/
├── manifest.ts          ← kind: "tool"
├── index.ts             ← AUTO-GENERATED
└── server/
    └── tools.ts

skills/<slug>-companion/
└── SKILL.md             ← optional but recommended
```

### Differences from `kind: "ui"`

- No `types.ts`, no `InputSchema`, no `ArtifactExtras`, no `BaseArtifact`.
- No Form, List, or Detail pages — host renders an auto-generated **About page** with a Try-it panel listing each tool, its description, schema, and an inline form to invoke it (browser-callable per §15).
- No companion-specific `_get` / `_update_status` / `_save_artifact` MCP tools — only the `defineTool()` entries the companion authors.
- Skill body is typically a brief "use these tools when X" guide rather than a step-by-step playbook. Optional, but recommended so Claude knows when the tools are relevant.

### Manifest

```ts
export const manifest: Manifest = {
  name: "weather",
  kind: "tool",
  displayName: "Weather",
  icon: "⛅",
  description: "Fetch current conditions and forecasts via OpenWeather.",
  contractVersion: "2",
  version: "0.1.0",
  requiredEnv: ["OPENWEATHER_API_KEY"],
};
```

Everything else (proxy-tool authoring, `defineTool` shape, error classification) is identical to `kind: "ui"`.
